# Recovery and delivery

- For direct upload, request a ticket with the exact file size and type. PUT bytes with the returned Content-Type and signed URL. Send the i2v.ai API key only to the i2v.ai API origin for ticket creation and completion. Use the verified URL in the model's actual reference field.
- Query `GET /api/v1/jobs/submission` with the original `Idempotency-Key` and credential. On `accepted`, fetch `GET /api/v1/jobs/recordInfo` by task ID. On `pending`, respect `Retry-After` and recheck. On `retryable`, replay the exact original request and key. On `rejected`, display the error. Treat HTTP 404 as an unconfirmed receipt and check the original credential and key before replaying it.
- Process webhooks from the exact raw request bytes. Look up the configured secret by `X-I2V-Key-ID` and verify the versioned HMAC over the timestamp, a dot, and the raw body. Enforce freshness, deduplicate by `X-I2V-Event-ID`, and apply the update only to the owned task. Keep a terminal state after receiving an older notification. Verify the event schema and header format against the [webhook documentation](https://i2v.ai/docs/webhooks).
- For a low-code workflow, start with an HTTP credential, quote step, an explicit approval or preconfigured USD limit, and a stable workflow operation ID. Store the job reference before allowing retries. Route the result to the destination only after success. If the workflow engine cannot access the raw webhook bytes, use bounded polling or validate the webhook in your own server before passing it onward.
